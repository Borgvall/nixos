# Project rules for coding agents (Claude Code, opencode & co.)

This repository is a personal NixOS flake configuration, not an application:
there is no compiler, no test suite and no CI. The only real verification is
"Nix can evaluate this host's configuration"; the only real test is the user
rebooting into it. The rules below stand in for the safety nets that a
programming project would provide - follow them proactively.

`Readme.md` describes the layout for humans. Keep *it* in sync when the
structure changes, instead of growing this file with structural prose.

## 1. Verify with `nixos-rebuild dry-build` before every commit

```bash
nixos-rebuild dry-build --flake .#johannes-pc
```

This evaluates the configuration of that host and prints what would be built
or downloaded - it builds nothing and activates nothing. It takes a few seconds
with a warm store and works as a normal user, no `sudo` needed.

Changes that don't touch a `.nix` file (this document, `Readme.md`) don't need
the check. Changes under `pkgs/` need more than an evaluation - they need a real
build, see rule 5.

Choose a host that actually imports what you changed:

- Shared modules (`configuration.nix`, `sway.nix`, `vim.nix`,
  `host-specific-options.nix`, ...) are imported by every host, so check any
  host that has the affected `hostSpecifics` setting switched *on*.
- Host-only modules (`ai.nix`, `gaming.nix`, `virtualization.nix`) are imported
  from a single `hosts/<name>/configuration.nix`; check exactly that host.

For a check that never even asks the builder, evaluate the derivation path
directly:

```bash
nix eval --raw .#nixosConfigurations.johannes-pc.config.system.build.toplevel.drvPath
```

Nix evaluates lazily and per attribute, so a successful `dry-build` of one
host proves nothing about a module that only another host imports. Check each
affected host.

If a host cannot be evaluated on this machine at all (e.g. a
`hardware-configuration.nix` that is only generated on the target machine),
verify with a host that shares the changed modules and state clearly which host
you checked and which you could not.

## 2. Untracked files do not exist for Nix

Flake evaluation copies the working tree through `git ls-files`, so anything
not `git add`ed is invisible. A brand-new module then fails with

```
error: Path 'hosts/foo/configuration.nix' does not exist in Git repository
```

even though the file sits right there in the working tree. Add new files with
`git add` *before* evaluating, and don't go hunting for a broken import.

## 3. Never activate a configuration yourself

`switch`, `boot`, `test` and `dry-activate` change the running machine - and
that machine is the user's live desktop, not a sandbox. Don't run them, and
don't try to "verify" a desktop change by driving the GUI with simulated
input.

Instead, do the evaluation check from rule 1, then hand the activation to the
user (`sudo nixos-rebuild switch --flake .#<host>`) together with a short,
concrete checklist of what to look at afterwards.

## 4. New hosts follow the existing layout

A host is a directory `hosts/<name>/` with `configuration.nix` and its
`hardware-configuration.nix`, plus an entry in `flake.nix`'s
`nixosConfigurations`. `hardware-configuration.nix` is generated by
`nixos-generate-config` on the target machine; don't hand-write or "repair" it,
regenerate it and keep the result as-is (including the comment noise).

`hosts/<name>/configuration.nix` only holds what is specific to that machine:
`networking.hostName`, `system.stateVersion`, `hostSpecifics` values, imported
hardware/filesystem modules, and imports of topical modules that only this host
needs. Everything host-independent lives in a root-level `*.nix` module.

## 5. Packages belong under `pkgs/` - and are built, not just evaluated

Anything this configuration needs but nixpkgs doesn't provide lives in `pkgs/`:
as a single `pkgs/<name>.nix`, or as `pkgs/<name>/package.nix` when the
definition needs sibling files. It is instantiated at the call site with
`pkgs.callPackage <path> {}` (see `development.nix` and `vim.nix`). Don't
inline a derivation in a system module, and don't smuggle a package in through
an overlay.

Keep the shape of the existing definitions: `version`, `rev = "v${version}"` in
`fetchFromGitHub`, and the usual `meta` attributes (`description`, `homepage`,
`license`, `mainProgram`) - that keeps a bump down to a version line plus a new
hash. Keep `subPackages`/`vendorHash` if the upstream needs them.

Evaluation cannot tell whether a package definition is actually correct: a
wrong `vendorHash`, a missing `subPackages` or a build-only dependency only
shows up when the build runs. So whenever you touch something under `pkgs/`, or
the module that instantiates it, do a real build of an affected host instead of
`dry-build`:

```bash
nixos-rebuild build --flake .#johannes-pc
```

This evaluates *and* builds the whole system into the store - still without
activating it, without a boot entry and without `sudo`. It leaves a `result`
symlink in the repository root; that is a build artifact (rule 10), not
something to commit. With a warm store it is as quick as `dry-build`; expect
minutes when the package itself still has to be fetched and compiled, so don't
start it right before a commit if you are unsure it will pass.

## 6. Host differences go through `hostSpecifics`, not hostname checks

`host-specific-options.nix` exists so that shared modules stay free of
`if config.networking.hostName == "..."` branches. When a shared module needs
to behave differently per host, add an option under `options.hostSpecifics`
(with type, default and description), use it in the shared module, and set it
in the affected `hosts/<name>/configuration.nix`. Follow the shape of the
existing `preferVulkan`, `interfaceNames` and `extraPrograms` options.

## 7. `system.stateVersion` is written once and never changed

It records the release a host was installed with and only makes sense as a
historical value. An "outdated" state version is correct; bumping it silently
changes migration behaviour and is never part of an unrelated change.

## 8. Input updates are their own commit

`nix flake update` (or touching `flake.lock` at all) goes into a separate
`Chore: nix flake update` commit, exactly like the existing history. It makes
an otherwise reviewable change unreviewable and is impossible to bisect
through.

## 9. Formatting and language

The repository follows `nixfmt` (RFC style) with two-space indentation, a
`{ pkgs, ... }:` header and a blank line before the attribute set. A few files
still deviate slightly; don't fix them as a side effect of an unrelated change,
because reformatting buries the actual diff.

- `nixfmt FILE` rewrites the file **in place** and prints nothing (use the
  `nixfmt -` stdin form if you want the output); `nixfmt --check FILE` only
  reports. `nixfmt` comes from `development.nix`, and `flake.nix` has no
  `formatter` output, so `nix fmt` is not available.
- Format files you create or rewrite completely; leave the formatting of files
  you only edit locally alone.
- New comments, docstrings and documentation are written in English. Some
  older comments are German - that's fine to leave untouched, but don't add
  new ones in German.
- No secrets in this repository: there is no sops/agenix setup, so real
  passwords, keys and tokens don't belong in a `.nix` file. Keep the
  `initialPassword`-style placeholders that are already there.
- Don't commit editor swap files, `result` symlinks or other build artifacts.

## 10. Commit messages

First line: at most 80 characters, starting with one of `Feat:`, `Fix:`,
`Refactor:`, `Tests:`, `Docs:` or `Chore:`, optionally narrowed with a scope in
parentheses - matching the existing history, e.g.

```
Feat(developement): install opencode and agent-lsp
Fix(sway): small fixes
Chore: nix flake update
```

Add a body when the change is not obvious from the diff: the first paragraph
summarises the requirement or the prompt that led to the change, the following
paragraphs summarise the design decisions and the alternatives that were
rejected.

Commits created by an agent are authored by that model, not by the user:

```bash
git commit --author="DeepSeek V4.1 Flash <no@reply.org>"
```

## 11. Use agent-lsp for code intelligence, not shell archaeology

`agent-lsp` is packaged in `pkgs/agent-lsp.nix` and wired up for this
repository in `.mcp.json` as `nix:nixd`, so it speaks the Nix language server
for `*.nix` files. Prefer its tools over `Grep`/`Read`-and-scan and over
poking around in `flake.lock` by hand:

| Task                     | Use this              | Not this                  |
| ------------------------ | --------------------- | ------------------------- |
| File structure / symbols | `list_symbols`        | `Read` + manual scanning  |
| Find a symbol by name    | `find_symbol`         | `Grep` across the repo    |
| All usages of a symbol   | `find_references`     | `Grep` for the name       |
| Understand a symbol      | `inspect_symbol`      | `Read` the whole file     |
| Who calls this function  | `find_callers`        | `Grep` for the name       |
| Replace a function body  | `replace_symbol_body` | `Edit` with text matching |
| Blast radius before edit | `blast_radius`        | guessing from the diff    |

Use `preview_edit` before applying a non-trivial edit and `get_diagnostics`
afterwards. Two standard parts of the generic agent-lsp recipe do **not** apply
here: there is no build system to `run_build` (use `nixos-rebuild dry-build`
from rule 1) and no test suite to `run_tests`. Don't invent one, and don't
trust a green `get_diagnostics` as proof that the host still evaluates.

`CLAUDE.md` carries the auto-generated agent-lsp tool and skill catalog
(`agent-lsp init` rewrites it). That block is the catalog; this section is the
project-specific guidance.

## 12. Plan a commit sequence before doing the work, not after

Every commit has to pass rule 1 on its own (evaluate, and for `pkgs/` changes
also build), so a finished working tree cannot be split into a reviewable
sequence for free - each intermediate state has to be reconstructed and
re-checked by hand. If a change wants more than one commit (a new host plus a
module fix, a package bump plus its consumer change, an input update), do it in
that order and commit as you go.
